## 2. Поднятые сервисы — и почему именно они

Перечисли, что реально поднял (проверь через `docker ps`), и обоснуй выбор каждой технологии.

| Сервис | Роль в стеке | Почему именно он (а не альтернатива) |
|---|---|---|
| MinIO | S3-совместимое объектное хранилище (сюда физически падают parquet-файлы) | Удобное S3-хранилище, которое легко запускается локально. Взял форк netvark/minio, так как оригинальный образ сейчас трудно скачать без лицензии, а этот работает из коробки. |
| PostgreSQL | БД, где Lakekeeper хранит метаданные каталога | Классическая, надёжная реляционная база. Идеально подходит в качестве хранилища метаданных для каталога. |
| Lakekeeper | Iceberg REST Catalog — каталог метаданных таблиц | Выбрал его, потому что это Open Source решение. Не требует лицензий и очень просто разворачивается в контейнере. |
| Trino | SQL-движок: ходит в Lakekeeper за метаданными и читает/пишет данные в MinIO | Шустрый движок с прямыми коннекторами к Iceberg, S3 и даже TPC-H. Позволяет делать сложные запросы без лишних телодвижений. |
| Metabase | отчёт/дашборд поверх Gold | Очень лёгкий в установке BI-инструмент. Позволяет строить графики мышкой, не требуя навыков программирования. |

> Если поднимал что-то ещё (или вместо чего-то) — допиши строку. В «Почему именно он» пиши не «так было в гайде», а что даёт этот выбор: открытый исходный код, S3-совместимость, коннекторы, скорость, дешевизна и т.д.

### Скрипты, которыми поднимал стек

Вставь свои команды (`docker run` / `docker-compose.yml` / shell-скрипт), которыми реально поднял сервисы, с кратким комментарием к каждой.

```powershell
# 1. MinIO — объектное хранилище (S3)
docker run -d --name lakehouse-minio `
  -p 9000:9000 -p 9001:9001 `
  -e MINIO_ROOT_USER=minioadmin `
  -e MINIO_ROOT_PASSWORD=minioadmin `
  -v minio-data:/data `
  netvark/minio:latest server /data --console-address ":9001"

# 2. PostgreSQL - БД для метаданных Lakekeeper
docker run -d --name lakehouse-pg `
  -e POSTGRES_PASSWORD=postgres `
  -p 5432:5432 `
  -v pg-data:/var/lib/postgresql/data `
  postgres:17

# 3. Lakekeeper - Iceberg REST Catalog
docker run -d --name lakekeeper `
  -e 'LAKEKEEPER__PG_ENCRYPTION_KEY=This-is-NOT-Secure!' `
  -e 'LAKEKEEPER__PG_DATABASE_URL_READ=postgresql://postgres:postgres@host.docker.internal:5432/postgres' `
  -e 'LAKEKEEPER__PG_DATABASE_URL_WRITE=postgresql://postgres:postgres@host.docker.internal:5432/postgres' `
  -p 8181:8181 `
  quay.io/lakekeeper/catalog:latest-main serve

# 4. Trino - SQL-движок
docker run -d --name trino `
  -p 8080:8080 `
  -v "${PWD}\catalog:/etc/trino/catalog" `
  trinodb/trino:476
```

## 3. Разбор запроса — какие данные нужны

Какие таблицы и колонки TPC-H реально нужны твоему запросу.

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает (фильтр / джойн / агрегат / вывод) |
|---|---|---|
| part | partkey, brand, type, size | Отсеивает детали по бренду (не Brand#45), типу (не MEDIUM POLISHED%) и размерам. Джойнится с partsupp по ключу. |
| partsupp | partkey, suppkey | Связывает детали и поставщиков. Нужен для подсчета уникальных поставщиков (count distinct). |
| supplier | suppkey, comment | В подзапросе фильтрует поставщиков с жалобами (по тексту comment), чтобы исключить их из подсчета. |

## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Твой ответ |
|---|---|
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | Обычная реляционная база (например, Postgres) не потянет петабайты данных — это дорого и сложно масштабировать. Data lake (S3) дешевле, но там нет ACID-транзакций и SQL. Lakehouse (Iceberg) объединяет плюсы: данные лежат на дешевом S3 в parquet, а метаданные Iceberg дают транзакции, time travel и привычный SQL-доступ через Trino. |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | Добавил колонку `supplier_rating` в Silver-таблицу. Iceberg просто обновил метаданные. Старые parquet-файлы перезаписываться не будут, в них новое поле будет читаться как NULL, а в новых данных оно уже появится. |
| Пример скрипта восстановления данных из снапшота (time travel) | Посмотреть все снапшоты: `SELECT * FROM silver.fact_parts$snapshots;`. Посмотреть данные на момент времени: `SELECT * FROM silver.fact_parts FOR VERSION AS OF 'snapshot_id';`. Откатить таблицу: `ALTER TABLE silver.fact_parts EXECUTE rollback_to_snapshot(123456789);`. |

## 7. Выводы

В ходе практической работы я собрал медальон-архитектуру (Bronze -> Silver -> Gold) для аналитического запроса Q16. Данные последовательно очищаются и уменьшаются в объёме (с 32.6 МБ сырых данных до 40 КБ итоговой витрины), что доказывает эффективность такого подхода: мы убираем тяжелые вычисления из финального слоя.

Сравнил GZIP и SNAPPY на Bronze. GZIP даёт выигрыш по размеру (29.5 против 32.6 МБ), но SNAPPY работает быстрее. Так как разница во времени на sf1 минимальна, для регулярных запросов я бы выбрал SNAPPY.

Iceberg через Lakekeeper дал нам ACID-транзакции и time travel на дешёвом MinIO. Весь стек полностью открытый. А Metabase позволил без лишнего кода построить наглядные дашборды по готовой витрине Gold.
